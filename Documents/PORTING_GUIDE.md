# 이식 가이드 (Porting Guide)

**원본**: `newslg-resource-planner` (`D:\02_SourceCode\newslg-resource-planner\resource-planner.html`) — "천하결전" 성내 건물 자원 계산기
**대상**: `sgzzlb_tech_tree` (이 프로젝트) — "삼국지 전략판" 용으로 재구성

이 문서는 원본 프로젝트에서 무엇을 그대로 가져오고, 무엇을 게임에 맞게 새로 설계해야 하는지, 그리고 어떤 순서로 작업하면 되는지를 정리합니다. 코드 레벨의 줄 단위 분석은 [CODE_STRUCTURE.md](./CODE_STRUCTURE.md)를 참고하세요.

> 지금 이 디렉토리의 `resource-planner.html`은 원본을 **그대로 복사**만 해 둔 상태입니다. 아직 삼국지 전략판에 맞게 손댄 부분은 하나도 없습니다 — 진짜 작업은 지금부터입니다.

## 1. 원본이 실제로 하는 일 (한 문장 요약)

사용자가 "이 건물을 몇 레벨까지 올리고 싶다"를 입력하면, 필요한 자원량을 합산하고, 현재 보유 자원·시간당 생산량·자원 상자/특수 아이템을 반영해 **완료 시각을 계산**하고, **가진 자원을 어디에 먼저 쓰는 게 최적인지**를 알려주는 도구입니다. 이 "목표 → 필요 자원 합산 → 완료 시간 시뮬레이션 → 최적 배분"이라는 뼈대는 성장형 SLG라면 게임이 달라져도 거의 그대로 쓸 수 있습니다. 달라지는 건 "자원이 몇 종류인지, 건물/기술이 뭔지, 비용 공식이 뭔지" 같은 **게임 고유 데이터와 규칙**입니다.

## 2. 그대로 재사용할 것 (아키텍처 · 패턴)

이 항목들은 **개념/코드 구조**를 그대로 가져다 쓰고, 게임 데이터만 바뀌는 부분입니다.

| 재사용 대상 | 원본 위치 | 왜 그대로 쓰는가 |
| :--- | :--- | :--- |
| 단일 HTML 파일 구조 (빌드 도구 없음, IIFE 캡슐화) | 전체 | 배포·공유가 가장 쉬운 형태. 삼국지 전략판 버전도 굳이 React/빌드 체인으로 바꿀 이유 없음 |
| CSS 커스텀 프로퍼티 기반 디자인 시스템 (라이트/다크 모드) | `<style>` | 색상 **값**만 자원 팔레트에 맞게 바꾸면 됨. 토큰 구조 자체는 유지 |
| 단방향 데이터 흐름 (입력 → 상태 갱신 → `render()` 파이프라인) | 메인 IIFE 전체 | 계산기류 UI에서 검증된 패턴. 상태 객체(`cur`/`tgt`/`boxes` 등)와 렌더 함수 이름만 게임에 맞게 리네이밍 |
| 이벤트 위임 (`document`에 `input`/`change`/`click`/`wheel` 한 번씩만 바인딩) | 이벤트 바인딩 구간 | 동적으로 다시 그려지는 표가 많은 UI에 필수적인 패턴 |
| **포커스/커서 보존 렌더링 기법** — `syncRoster()`의 "활성 input이면 값 갱신 skip", `renderOptResTable()`/`renderOptGoalTable()`의 "activeId/activeVal 저장 → 재렌더 → 재포커스 → `restoreCaretToEnd()`" | `syncRoster`, `renderOptResTable`, `renderOptGoalTable`, `restoreCaretToEnd` | **오늘([CHANGELOG](../../newslg-resource-planner/Documents/CHANGELOG.md) 참고) 두 번에 걸쳐 직접 겪은 버그**입니다. 표를 매 키 입력마다 `innerHTML`로 다시 그리면 (1) 포커스가 끊기거나 (2) 포커스는 유지돼도 새로 만들어진 input이 값 전체를 선택 상태로 만들어 다음 숫자가 이전 값을 덮어씁니다. 새 프로젝트에서 레벨/수량 입력 표를 다시 만들 때 **이 두 가지를 처음부터 피해서 설계**하세요. 가장 쉬운 회피법은 표를 통째로 다시 그리지 않고 `syncRoster`처럼 셀 단위로 patch하는 것입니다 |
| `localStorage` 자동 저장/복원 (`saveState`/`loadState`) | `saveState`, `loadState` | 키 이름과 저장 필드 구조만 새로 정의 |
| 커스텀 툴팁 서브시스템 (`#tip`, hover 좌표 추적) | 툴팁 이벤트 바인딩 구간 | 건물/기술 hover 설명에 그대로 재사용 가능 |
| 숫자 input 위 마우스 휠로 값 증감 (`wheel` 이벤트, Shift = ×10) | `wheel` 이벤트 바인딩 | UX 패턴으로 그대로 재사용 가능 |
| "현재/목표" 2단 입력 + 구간 비용 누적(`costRange` 패턴) | `costRange`, `plan` | 레벨업형 재화 계산의 공통 패턴. 비용 필드 개수/이름만 게임에 맞게 조정 |
| 그리디 2단계 배분 알고리즘의 **아이디어** (병목 자원부터 해소 → 남는 걸로 아껴두기 교체) | `allocate` | "여러 소스를 어디에 먼저 쓸지" 최적화 문제 자체는 게임이 달라도 동일한 구조. 단, 삼국지 전략판에 "자원 상자/둔전" 같은 대응 시스템이 있는지부터 확인 필요 (§3) |

## 3. 반드시 새로 설계해야 할 것 (게임 고유 데이터/규칙)

이 항목들은 **삼국지 전략판의 실제 게임 데이터를 확인하기 전까지는 손댈 수 없는 부분**입니다. 코드를 옮기는 것과 별개로, 아래 정보부터 확보하는 게 우선입니다.

| 항목 | 원본(천하결전)에서의 모습 | 확인/설계 필요 사항 |
| :--- | :--- | :--- |
| 자원 종류 | 목재/철광/석재(+군량) 3~4종, `RES = ["w","i","s"]` | 삼국지 전략판의 자원 종류·개수·이름은? (목재/철/식량/은 등 다를 가능성) |
| 건물/기술 데이터 스키마 | `#gd` JSON: `{건물명: {type, levels: {레벨: {w,i,s,g,p,e}}}}` | 삼국지 전략판은 "건물 레벨업"이 아니라 **기술 트리**(선행 기술, 분기, 티어)일 수 있음 → 프로젝트명이 `tech_tree`인 것도 이 때문으로 보임. 트리 구조(선후 관계, 분기, 병렬 연구)라면 원본의 "건물 목록 flat list" 스키마로는 부족하고, 그래프/트리 구조(`prerequisites: []` 등)로 다시 설계해야 함 |
| 비용 비율 공식 | 목:철:석 = 3:3:4 고정 | 삼국지 전략판 자체 비율/공식 확인 필요. 게임마다 자원별 비율이 다르고, 티어가 오를수록 비율이 바뀌는 경우도 있음 |
| 특수 획득 수단 (상자/둔전/군둔) | 자원 상자 4종(5천/1만/2만/10만), 둔전(개간지 레벨 기반, 자원 건물 20레벨 시 배율 보너스) | 삼국지 전략판에 대응하는 시스템이 있는지, 있다면 규칙이 무엇인지 확인. 없다면 이 로직(§2의 `allocate`, `duntianYield` 등)은 걷어내야 함 |
| 영지/개간지 생산 시스템 | 외성 영지 + 내성 개간지, 레벨별 고정 생산량, 버프% | 삼국지 전략판의 생산 시스템(둔전/영지/시설) 구조 확인 필요 |
| 창고 상한 등 제약 조건 | `warehouse_capacity` 효과 키 | 자원 상한이 존재하는지, 초과 시 페널티가 있는지 확인 |
| 번영도(prosperity) 같은 부가 지표 | `p` 필드 | 삼국지 전략판에 대응하는 지표(세력치/명성 등)가 있는지 확인 |

> ⚠️ 위 표의 오른쪽 칸을 채우기 전까지는 §5의 "데이터 스키마 재정의" 단계로 넘어갈 수 없습니다. 가장 먼저 할 일은 코드가 아니라 **삼국지 전략판의 실제 건물/기술 데이터를 표(CSV/JSON)로 확보하는 것**입니다. (`sgzzlb_hooking`, `sgzzlb_mapMaker` 프로젝트에 관련 추출 도구/가이드가 이미 있다면 그쪽을 먼저 확인하세요.)

## 4. 진행 순서 제안

1. **데이터 확보** — 삼국지 전략판의 기술 트리(또는 건물) 전체 목록, 레벨/티어별 비용, 선후행 관계, 효과를 원시 데이터로 수집. 가능하면 CSV 하나로 정리 (원본의 `main_city_building_levels.current.csv`처럼).
2. **구조 결정** — 위 데이터가 "flat 레벨업 리스트"인지 "진짜 트리(분기·선행조건 있음)"인지 확정. 트리라면 UI도 원본의 "표 렌더링" 방식이 아니라 노드-엣지 형태의 시각화가 필요할 수 있음 → 이 경우 이번 세션에서 상의가 더 필요함 (아래 §6 참고).
3. **DATA_SPEC 정의** — 새 JSON 스키마를 확정하고, `resource-planner.html`의 `#gd` 데이터 블록을 교체.
4. **전역 상수 교체** — `RES`, `RNAME`, `RVAR`, `RTO`, `EFFECT_LABEL`, `BOX_SIZES` 등을 새 게임 값으로 재정의 ([CODE_STRUCTURE.md §2](./CODE_STRUCTURE.md) 참고).
5. **탭 구성 재검토** — 원본 4탭(목표 자원 계산 / 생산량 계산 / 최적 선투자 탐색 / 주요 건물 최적화) 중 삼국지 전략판에 의미가 있는 탭만 남기고, 필요하면 트리 시각화 탭을 새로 추가.
6. **계산 로직 이식** — §2의 재사용 가능한 함수는 그대로 옮기고, §3의 게임 종속 로직(비율 공식, 상자/둔전 등)은 새로 작성.
7. **입력 UI 재구성 시 포커스 버그 재발 방지** — 표를 매 키 입력마다 통째로 다시 그리는 패턴을 쓰지 않거나, 쓸 수밖에 없다면 `restoreCaretToEnd()` 패턴을 처음부터 적용 (§2 참고).
8. **문서 갱신** — 원본의 `Documents/` 세트(ARCHITECTURE·DATA_SPEC·CALCULATION_LOGIC·USER_GUIDE·CHANGELOG·TODO)를 이 프로젝트에도 동일한 구성으로 만들어 유지.

## 5. 지금 당장 결정이 필요한 것

- **"기술 트리"가 원본처럼 단순 레벨업(1→N)인지, 실제 분기/선행조건이 있는 트리인지** — 이건 UI 설계 자체를 좌우하는 가장 중요한 결정이라, 데이터를 보기 전엔 코드 이식 작업을 더 진행하기보다 이 확인부터 하는 걸 권장합니다.
- 자원 상자/둔전에 대응하는 삼국지 전략판 시스템 유무.
- 어떤 탭(목표 계산/생산량/선투자 추천/건물 최적화)이 삼국지 전략판에도 의미가 있는지.
