## 5. 탭1(목표 자원 계산) 데이터 이식 (2026-08-20 세션)

`resource-planner.html`을 실제 sgzzlb 데이터로 이식하는 첫 실작업. 코드를 파본 결과 PORTING_GUIDE.md가 예상한 것보다 범위가 컸음 — `RES` 상수 하나만 바꾸면 되는 게 아니라 `costRange`/`state`/`plan`/`renderRoster`/`renderNeed`/`allocate` 등 수십 곳에 `{w,i,s}`가 개별적으로 하드코딩돼 있었음. 사용자와 상의해 **이번 세션은 탭1만 완성도 높게 만들고, 탭2~4와 둔전/자원상자/군둔/생산전환은 다음 단계로 미루는 것**으로 범위를 좁혔음.

### 5.1 데이터 변환
- `Documents/data/buildings.json`(27개 건물, `{cost:{w,i,s}, effect?}` 스키마)을 원본의 `GD` 스키마(`{type, levels:{lv:{w,i,s,f,p}}}`)로 변환하는 PowerShell 스크립트를 1회성으로 작성·실행 (저장 안 함, 필요하면 이 로그의 매핑 규칙 참고해 재작성).
  - `w`/`i`/`s`는 원본 그대로, `f`(식량)는 항상 0 — sgzzlb.xlsx "건물자원" 시트에 건물 업그레이드 비용으로서의 식량 데이터가 없기 때문. `p`(번영도)도 항상 0 — 삼국지 전략판에 대응 지표가 아직 확인되지 않아서.
  - 원본의 구조화된 `e:{add_wood_production:100,...}` 효과 객체 대신, sgzzlb 데이터의 자유 텍스트 `effect`("식량 생산량 +100" 등)를 `eff` 문자열 필드로 그대로 보존. `tipFor()`(건물 이름 hover 툴팁)를 이 텍스트를 그대로 보여주는 방식으로 재작성.
  - 변환 결과를 `resource-planner.html`의 `<script id="gd">` 블록에 그대로 삽입.
- `RES`를 `["w","i","s"]` → `["w","i","s","f"]`(식량 추가)로 확장하고, 이 변경으로 실제 영향받는 모든 지점을 수정: `RNAME`/`RVAR`/`RTO`, CSS `--food` 변수(라이트/다크 테마 모두), `costRange`/`state`/`plan`/`gdLumps`/`allocate`의 `{w,i,s}` 객체 리터럴에 `f` 추가, 탭1 HTML에 `have_f`/`rate_f` 입력 필드 추가(그리드를 3열→4열로), 로스터 테이블 헤더에 "식량" 열 추가, `saveState`(기존에 `have`/`rate` 저장 시 `f`가 빠져 있던 버그도 함께 발견해 수정).

### 5.2 원본 전용 시스템 비활성화 (삭제 아님)
목표는 "탭1 정확도"였으므로, 아직 설계되지 않은 시스템이 활성 상태로 남아 **그럴듯하지만 틀린 숫자**를 보여주는 것을 막는 데 집중:
- 둔전/군둔/자원 상자/생산 전환("영지 스왑") 카드를 `display:none`으로 숨김. **DOM 요소 자체는 삭제하지 않음** — 이 네 기능이 코드 전역(`allocate`/`loadState`/`gdLumps` 등)에서 서로 얽혀 있어, 요소를 지우면 `null.checked` 같은 참조 오류가 날 위험이 컸음. 체크박스 기본값도 전부 off로, 상자 개수 기본값도 0으로 변경.

- 부정확한 정보였던 텍스트 정리: "목:철:석 = 3:3:4 고정 비율" 안내(원본에만 해당), "번영도" 히어로 카드(sgzzlb 데이터에 없는 지표) 제거. `renderFoot()` 데이터 출처 안내를 sgzzlb.xlsx 기준으로 갱신.

## 7. sgzzlb.xlsx에 "카테고리" 열 추가 반영 (2026-08-20, 같은 세션)

사용자가 `sgzzlb.xlsx` "건물자원" 시트를 직접 수정해 각 건물 그룹 앞에 "카테고리"(내정/군사/수비) 마커 행을 추가함. 재파싱해 반영:

- `Documents/data/buildings.json` 각 건물에 `cat` 필드 추가. 파싱은 xlsx의 `카테고리` 마커 컬럼을 그룹 경계로 사용하는 방식으로 재작성(기존의 "다음 건물명 등장까지" 휴리스틱보다 안정적).
- **덤으로 발견한 것**: `창고` 레벨 8·9·10에 그동안 비어 있던 `effect` 텍스트가 채워짐("최대 자원 +250000/+300000/+350000"). 다만 레벨 11~19는 여전히 비어 있어 창고 상한 완전 복구는 아직 안 됨 — §5.2에서 언급한 `cap = Infinity` 임시 조치는 그대로 유지.
- xlsx에 **"군사부" 건물 데이터가 새로 추가됨** — 그런데 **3레벨까지만 채워져 있고, 그 수치가 사용자가 채팅으로 준 5레벨 데이터와 어긋남**: xlsx는 1→(5000,5000,10000), 2→(20000,20000,40000), 3→(30000,30000,60000)인데, 채팅으로 받은 값은 1→(5000,5000,10000), 2→(10000,10000,20000), 3→(15000,15000,30000), 4→(20000,20000,40000), 5→(30000,30000,60000). **xlsx의 "2행"·"3행" 값이 채팅 기준 "4레벨"·"5레벨" 값과 정확히 일치** — 아마 스프레드시트에 2·3레벨 행을 빠뜨리고 4·5레벨 값을 2·3 자리에 잘못 채운 것으로 추정됨. **이번엔 채팅으로 받은 5레벨 완전판을 그대로 신뢰**해서 `buildings.json`/GD에 반영했고, xlsx 쪽은 고치지 않았음 — 다음에 xlsx를 다시 저장하면 다시 어긋날 수 있으니 사용자가 스프레드시트의 2·3레벨 행을 확인해 주는 게 좋음.
- 이 파싱 스크립트도 1회성(저장 안 함) — 재파싱 필요하면 이 로그의 "카테고리 마커 = 그룹 경계" 규칙을 참고해 다시 작성.
- `resource-planner.html`의 `<script id="gd">`도 갱신된 데이터로 재삽입, jsdom 스모크 테스트로 31개 건물·카테고리 순서·계산 결과 재확인 완료.

## 8. 페이지 레이아웃 개편 — 아코디언·상단 요약·인라인 효과 (2026-08-20, 같은 세션)

### 8.1 건물 리스트를 카테고리별 펼쳐보기(아코디언)로 변경
`renderRoster()`를 다시 써서, 기존의 "한 표에 카테고리 구분 행" 방식 대신 카테고리(내정/군사/수비/분성)마다 별도의 `<details class="cat-block"><summary>카테고리 (N개)</summary><table>...</table></details>` 블록으로 분리. 페이지 로드 시 **첫 번째(내정)만 펼쳐진 상태**, 나머지는 접힌 상태로 시작 — 메인 페이지가 너무 길다는 피드백 반영. `syncRoster()`의 `#rosterWrap tr[data-b]` 선택자는 중첩된 테이블에도 그대로 걸리므로 계산 로직은 손대지 않음.

### 8.2 수동 입력을 카테고리 밖으로 분리
"수동 입력"은 더 이상 로스터 표의 한 행이 아니라, `#manualWrap`이라는 별도 DOM(카드 하단, 모든 카테고리 아코디언 다음)에 목재/철광/석재/식량 4칸짜리 `grid4` 입력으로 존재. 기존 `<tr id="manualRow">` 기반 active 하이라이트 로직도 `#manualWrap.active` 클래스 토글로 교체.

### 8.3 "완료까지"·"완료까지 걸리는 시간"을 전체 폭으로 상단/하단 배치
`#verdict`(완료까지/종료시각/병목자원/총필요/업그레이드 5개 히어로)를 `.layout`(사이드바+본문 2단 그리드) 밖으로 꺼내 `#tab-target`의 첫 자식으로 옮김 — 사이드바 폭에 눌리지 않고 페이지 전체 폭을 씀. `.verdict`도 `flex-wrap:nowrap`으로 바꿔 5개 항목이 항상 한 줄에 표시되게 함(700px 이하에서만 다시 wrap 허용). "완료까지 걸리는 시간"(`#needBody`) 카드도 같은 이유로 `.layout` 밖, 탭 맨 아래(푸터 바로 위)로 이동.

### 8.4 건물 효과를 hover 툴팁 대신 상시 인라인 칸으로
기존엔 건물 이름에 마우스를 올려야 `tipFor()`가 만든 텍스트가 커스텀 툴팁(`#tip`)으로 떴음. 이제 로스터 표에 **"효과" 칸**을 추가(건물 이름 바로 오른쪽)해서, `effInline(b)`가 만든 텍스트(모노스페이스 폰트, 옅은 색)를 항상 표시. 현재 레벨 효과와 목표 레벨 효과가 다르면 "Lv효과 → 목표Lv효과" 형태로 화살표 연결. `tipFor()`/`#tip` 커스텀 툴팁 자체는 그대로 남아있지만(다른 곳에서 쓰일 수 있어 삭제는 안 함) 로스터에서는 더 이상 사용 안 함.

### 8.5 "분성"(제2 거점) 카테고리 신규 추가
사용자 지시로 카테고리를 하나 더 추가: **분성** — 수비 다음 순서. 내정 경제 건물 7종(군왕전/창고/농장/채석장/벌목장/제련소/민가)을 `분성-`을 붙인 이름(분성-군왕전 등)으로 그대로 복제해서 담음. **비용 데이터는 원본과 완전히 동일** — 분성 전용 수치가 따로 있는지는 아직 확인 안 됐고, 사용자가 "이렇게만 넣어줘"라고 지시한 대로 우선 복제로 채워둔 상태. 실제 분성의 건물 비용이 본성과 다르다면 나중에 xlsx나 채팅으로 실제 수치를 받아 갱신 필요.

### 8.5-1 아코디언 다듬기 (같은 세션, 스크린샷 피드백 반영)
- 표 첫 칸(건물명)이 카드 왼쪽 벽에 거의 붙어 보인다는 피드백 → `th:first-child/td:first-child`의 `padding-left`를 2px→16px로, 전반적인 `td`/`th` 좌우 패딩도 8px→12px로 넓힘.
- `<summary>`의 ▸ 아이콘만으로는 클릭 가능한 토글인지 모호하다는 피드백 → 아이콘을 없애고 **"펼쳐보기"/"접기" 텍스트 버튼**(둥근 필 모양)을 summary 오른쪽에 명시. `<details>`의 네이티브 `toggle` 이벤트를 구독해 열림/닫힘에 따라 라벨을 실시간으로 바꿈. 기본 상태(내정만 열림)는 원래도 의도대로 동작 중이었음 — 사용자가 캡처한 화면은 직접 "군사"를 펼쳐본 상태였던 것으로 보임.

### 8.5-2 식량을 건물 비용에서 제외 + 건물별 포함 체크박스 (같은 세션)
- **식량은 건물 업그레이드 비용이 아니라는 사용자 확인** → 로스터 표(카테고리 아코디언 안)는 `RES`(4종) 대신 `BRES = ["w","i","s"]`만 렌더링하도록 `buildingRowHtml`/`ROSTER_HEAD`/`syncRoster`를 수정. **수동 입력 섹션은 그대로 4종(식량 포함)** 유지 — 건물이 아닌 다른 용도(예: 징병 등)로 식량이 필요할 수 있어서. `plan()`/`costRange`/needBody 등 전체 합산 로직은 그대로 둠 — 건물 비용 자체가 항상 식량 0이라 수치에는 영향 없고, 수동 입력으로 식량을 넣으면 여전히 총 필요·완료시간에 반영됨.
- **건물 이름 왼쪽에 체크박스 추가** — 체크 해제 시 그 건물은 목표 레벨(`tgt`)이 `cur`보다 높아도 `plan()`에서 완전히 제외됨(`chk[b]` 상태, 기본값 전부 체크). 즉 "목표는 잡아두되 지금 계산에는 넣지 않기"가 가능해짐. 체크 해제된 행은 `tr.excluded`로 반투명 처리. `chk` 상태도 `cur`/`tgt`처럼 `localStorage`에 저장/복원됨.

### 8.5-3 헤더 정렬 정리 + 카테고리 전체 선택 체크박스 (같은 세션)
- 로스터 표의 열 제목과 그 아래 값의 정렬이 서로 안 맞는다는 피드백 → `.roster table`의 열별(`nth-child`) 정렬을 데이터와 맞춤: 건물(좌), 효과(가운데), 최대(우, 그대로), 현재·목표(가운데 — 안의 `<input>` 숫자가 가운데 정렬이라 헤더도 맞춤), 목재·철광·석재(우, 그대로).
- "건물" 헤더 왼쪽에 **카테고리 전체 선택 체크박스**(`input.cat-all-chk`) 추가. 클릭하면 그 카테고리에 속한 모든 건물의 `chk[b]`를 한 번에 켜거나 끔. 일부만 체크된 상태면 헤더 체크박스가 **미정(indeterminate)** 표시로 나타남. `CAT_BUILDINGS`(카테고리→건물명 배열)를 `renderRoster()`에서 캐싱해 `syncRoster()`/체인지 핸들러가 재사용.

### 8.5-4 체크박스 기본값 반전 + 수동 입력 체크박스 (같은 세션)
- 건물 체크박스 기본값을 **전부 미체크**로 변경(`chk[b]` 기본 `false`). "목표 레벨만 잡아놓고 계산엔 아직 안 넣기"가 기본 상태가 됨.
- `tr.excluded` 스타일 의미를 재정의: 이제는 "체크 안 됐지만 목표는 현재보다 높게 잡혀 있어 계산에서 빠진 상태"만 표시(목표 칸 테두리를 점선으로) — 단순히 미체크인 것 자체는 기본 상태라 dim 처리하지 않음.
- "수동 입력" 타이틀 왼쪽에도 체크박스 추가(`manualChk`, 기본 미체크). 값이 있어도 체크해야 `plan()`에 반영됨. 카테고리 전체선택 체크박스와 마찬가지로 `localStorage`에 저장/복원.

### 8.5-5 둔전 · 보유 책서 (같은 세션)
사용자가 준 실제 규칙 반영:
- "보유 자원" 카드 제목(`h3.grp`) 오른쪽 끝에 **"보유 책서"** 라벨+입력칸(`have_scroll`)을 인라인으로 삽입(`.title-row`/`.inline-field`) — 별도 카드로 안 만들고 같은 카드 안에 넣어달라는 피드백 반영. (처음엔 별도 미니 카드로 만들었다가 이 요청으로 병합함.)
- "시간당 생산량" 바로 아래에 **"둔전"** 카드 신규 추가. `+ 둔전 추가` 버튼으로 행을 늘리고, 각 행마다 **획득 자원 종류**(`select`, 4종 전체 — 건물 비용과 달리 식량도 포함)와 **최대 토지**(숫자)를 입력. 삭제 버튼으로 행 제거. 상태는 `duntian = [{res, land}, ...]` 배열, `localStorage`에 저장.
- **1회당 책서 3개 소모**(`DT_SCROLL_COST = 3`, 사용자 확정 규칙) 그대로 반영 — 보유 책서 ÷ 3을 내림해 "최대 N회 둔전 가능" 요약을 실시간으로 보여줌(`syncDuntian()`).
- **주의**: "최대 토지"가 실제 자원 획득량으로 어떻게 환산되는지(토지 레벨→수확량 공식)는 아직 안 받아서, 이번 단계에서는 입력만 받고 `plan()`/완료시간 계산에는 반영하지 않음 — 카드 안내 문구에도 "다음 단계에서 반영 예정"이라고 명시. 공식을 받으면 총 필요 자원 계산에 연결 예정.
- 렌더링은 로스터와 같은 patch 패턴 사용: 행 추가/삭제 같은 구조 변경에만 `renderDuntianList()`(전체 재생성)를 쓰고, 값 입력은 `render()`→`syncDuntian()`(요약 문구만 갱신)로 처리해 입력 중 포커스가 끊기지 않게 함.

### 8.5-6 자잘한 수정
- 헤더 설명 문단(`<p>`)이 좁은 화면에서 2줄로 꺾이던 것을 `white-space:nowrap`(+ 필요 시 가로 스크롤)으로 한 줄 고정.

### 8.5-7 둔전 UI 단순화 (같은 세션)
- "행 추가/삭제 + 자원종류 select + 최대 토지" 방식(§8.5-5)을 사용자 피드백에 따라 **"시간당 생산량"과 동일한 고정 4칸 그리드**로 교체: `dt_w`/`dt_i`/`dt_s`/`dt_f` — 자원별 "1회 획득량"만 직접 입력받음. `duntian` 배열, `renderDuntianList()`, add/del 버튼과 관련 CSS(`.dt-row` 등)는 전부 제거. `syncDuntian()`은 이제 보유 책서÷3 요약 문구만 갱신.
- 저장/복원(`saveState`/`loadState`)도 배열 대신 `duntianRate:{w,i,s,f}` 형태로 단순화.
- 카드 맨 아래에 안내문 추가: "둔전 실시 화면에서 획득 자원을 입력하세요. 해당 건물 20레벨에서의 +50%버프는 별도로 계산하지 않습니다." — 사용자가 입력할 값의 기준(실제 둔전 실행 화면에 뜨는 수치)과, 아직 반영 안 된 변수(건물 20레벨 +50% 버프)를 명시.

### 8.5-8 체크박스가 실제로는 안 먹던 버그 수정 (같은 세션)
사용자가 "체크박스가 제대로 동작 안 하는 것 같다"고 신고 — 재현해보니 실제 버그였음.
- **원인**: 체크박스를 클릭하면 브라우저가 `"input"` 이벤트를 먼저 쏘고 그다음 `"change"`를 쏘는데, `chk[b]`/`manualChk` 상태 갱신은 `"change"` 리스너에만 들어 있었음. 그런데 `"input"` 리스너 맨 아래엔 `if (t.tagName === "INPUT") { render(); ... }`라는 범용 처리가 있어서, **체크박스의 `"input"` 이벤트에도 그게 걸려 render()가 먼저 실행됨**. 이때 `syncRoster()`가 (아직 `chk[b]`가 안 바뀐 상태이므로) 체크박스의 `.checked`를 **클릭 이전 값으로 도로 덮어써버림**. 그 직후 `"change"`가 발생해도 `e.target.checked`는 이미 되돌려진 값이라, 실질적으로 체크가 안 먹거나 다음 클릭까지 한 박자 밀리는 것처럼 보였음.
  - (기존에 있던 `use_box`/`use_dt`/`use_gd` 같은 체크박스들은 이 문제가 없었던 이유: 그것들은 별도 JS 상태 변수로 미러링하지 않고 렌더 시점에 `$("use_box").checked`를 직접 읽기만 해서, DOM에 다시 써넣는 이 되먹임이 애초에 없었음.)
- **수정**: `b-chk`/`cat-all-chk`/`manual-chk` 세 체크박스의 상태 갱신 로직을 `"change"` 리스너에서 `"input"` 리스너 맨 앞(범용 처리보다 먼저, `return`으로 종료)으로 옮김 — `"input"` 시점에 이미 `e.target.checked`가 새 값으로 확정돼 있으므로 그대로 상태에 반영하고 끝냄. `"change"` 리스너의 중복 처리는 제거.
- jsdom에서 `.click()`(실제 클릭처럼 input→change 순서를 그대로 재현)으로 건물 체크/해제, 카테고리 전체선택, 수동 입력 체크박스까지 전부 정상 동작 확인.

### 8.5-9 누적 비용 합계 · 건물 기본 레벨 0 · 둔전 안내문 정리 (같은 세션)
- 건물 리스트 힌트 문구 아래에 구분선(`hr.rule`)과 **"누적 비용"** 합계를 추가. `plan()`이 반환한 `pl.items`에서 "수동 입력" 항목은 제외하고 체크된 건물들의 목재/철광/석재만 합산해 표시(식량 제외는 §8.5-2와 동일한 이유). `syncRoster(pl)`로 `pl`을 넘겨받아 `#rosterTotal`을 갱신.
- **모든 건물의 기본 시작 레벨을 1 → 0으로 변경** — "여긴 0레벨이 존재해"라는 사용자 확인에 따름. 기존에 포팅 초기 데모용으로 넣어뒀던 군왕전=6, 벌목장/제련소/채석장/농장/민가=10, 징병소=3 같은 개별 기본값도 전부 제거하고 `BLIST.forEach(...cur[b]=0;tgt[b]=0...)`로 통일. `getCurLv()`의 fallback 기본값도 1→0으로 맞춤. (데이터의 레벨1 행이 이미 "0→1 비용"을 의미하므로 `costRange`/`bMax` 등 계산 로직 자체는 손댈 필요 없었음.)
- 둔전 카드의 "1회당 책서 3개 소모..." 동적 안내문 삭제(요약 숫자만 남김). 정적 안내문 문구를 "해당 건물 20레벨에서의 +50%버프는..." → "해당 건물 20레벨 +50% 추가 획득은 별도로 계산하지 않습니다."로 수정.

### 8.5-10 성지 보상 서신 카드 신규 추가 (같은 세션)
둔전 카드 바로 아래에 새 카드 "성지 보상 서신" 추가 — 5~10레벨 6칸, 각각 "보유 통수"를 입력. 레벨별 보상표(사용자 확정치, 서신 1통당 목재·철광·석재·식량 **전부 동일 수량**):

| 레벨 | 5 | 6 | 7 | 8 | 9 | 10 |
|---|---|---|---|---|---|---|
| 자원별 획득량 | 15,000 | 20,000 | 30,000 | 40,000 | 60,000 | 80,000 |

`SACRED_LEVELS`/`SACRED_REWARD` 상수 + `syncSacred()`로 "서신 N통으로 자원별 각 M" 요약을 실시간 계산(둔전과 달리 공식이 완전히 확정돼 있어 정확한 합계 표시 가능). 값은 `sacred_5`~`sacred_10` id의 평범한 입력칸이라 `saveState`/`loadState`에도 반영. **아직 "총 필요 자원"/완료 시간 계산에는 연결하지 않음** — 둔전과 마찬가지로 입력·요약만 우선 구현.

### 8.5-11 내정 카테고리 순서 조정 (같은 세션)
좌민부를 내정 카테고리 맨 아래로 이동(군왕전·창고·농장·채석장·벌목장·제련소·민가·원구단·좌민부 순). GD 변환 스크립트의 `$domesticOrder` 배열만 바꿔 재생성/재삽입.

### 8.5-12 군사 카테고리 순서 조정 (같은 세션)
군사 카테고리를 사용자가 지정한 순서로 재배열: 숙소·열병대·징병소·군사부·군영·사령단 → 병사전 4종 → 협력 4종 → 병영 5종. `$militaryOrder` 배열만 수정해 재생성/재삽입.

### 8.5-13 둔전 배분 추천 — 원본의 "상자·둔전 배분" 재구현 (같은 세션)
사용자가 원본(천하결전) 프로젝트에 있던 "모자란 자원에 상자·둔전을 추천 배분"하는 기능을 여기도 만들 수 있냐고 물어서 구현. §8.5-5/§8.5-7에서 "토지 레벨→수확량 공식을 몰라서 계산에 반영 못 함"이라고 미뤄뒀던 부분이, §8.5-7에서 둔전을 "자원별 고정 1회 획득량" 입력으로 단순화하면서 실은 완전히 계산 가능해진 상태였음 — 그래서 이번에 마저 연결.

- **원본의 `allocate()`(상자+둔전 2단계 그리디)를 `duntianPlan()`으로 교체**: 보유 책서÷3 = 총 사용 가능 횟수, 매 회마다 "지금 이 자원에 한 번 쓰면 완료 시각이 얼마나 당겨지는지"를 4개 자원 후보 전부 시도해보고 가장 크게 당겨지는 자원에 배분(더 당겨지는 후보가 없으면 중단 — 남은 횟수는 "아껴두기"). 원본의 2단계(그리디+스왑) 대신 1단계 그리디로 단순화했는데, 여기선 "상자 크기가 제각각이라 낭비가 생기는" 문제 자체가 없어서(자원마다 획득량이 고정) 스왑 단계가 필요 없음.
- `render()`의 `al = allocate(pl, st)` 호출을 `al = duntianPlan(pl, st)`로 교체 — `renderVerdict`/`renderNeed`는 원래도 `al.have`/`al.used`/`al.count`를 범용적으로만 참조하고 있어서 **수정 없이 그대로 재사용됨**. `renderAlloc()`만 상자 전용 표시(상자 크기별 개수) 로직을 걷어내고 "둔전 × N회" 형태로 다시 씀.
- 숨겨져 있던 "상자·둔전 배분" 카드를 **"둔전 배분 추천"**으로 이름 바꿔 다시 노출. 내부의 자원상자/군둔 체크박스(`use_box`/`use_gd`)는 아직 미이식이라 `display:none`으로 숨긴 채 DOM에는 남겨둠 — `renderSwap()` 등 다른 하위(아직 숨김) 로직이 그 요소들을 직접 참조해서, 지우면 참조 오류가 날 수 있어서.
- jsdom으로 검증: 석재만 부족한 시나리오에서 둔전 10회를 전부 석재에 배분 추천(완료 12일22.2h→5일23.5h), 4자원 전부 동일 획득량이어도 압도적으로 부족한 석재에 20회 전부 집중 배분되는 것까지 확인(단순 병목이 아니라 실제로 완료 시각을 줄이는 자원에만 쓰는 그리디가 맞게 동작).

### 8.5-14 출사 추가 + 둔전·성지보상·출사 통합 배분 엔진 (같은 세션)
"성지 보상 서신" 카드 바로 아래에 **"출사"** 카드 신규 추가 — 자원 4종 중 1종을 골라 1회당 **고정 8만**을 받는 소스(`CHULSA_AMOUNT=80000`, `chulsa_n` 입력 하나만 있으면 됨. 둔전처럼 자원별 금액이 다른 게 아니라 어느 자원에 쓰든 8만으로 고정이라 필드 하나로 충분).

§8.5-13에서 만든 `duntianPlan()`(당시 이름 그대로 유지, 지금은 둔전 전용이 아님)을 세 소스를 전부 반영하도록 확장:
- **성지 보상 서신**: 자원 선택지가 없이 4종에 똑같이 들어오므로 그리디 대상이 아니라 `have`에 무조건 먼저 더함.
- **둔전·출사**: 둘 다 "자원 하나를 골라서 받는" 방식이라 매 회 두 소스의 모든 (소스×자원) 후보를 같이 비교해서 완료 시각을 가장 많이 당기는 조합을 그리디로 선택 — 둔전 쪽이 더 유리하면 둔전을, 출사가 더 유리하면(자원별 획득량이 8만보다 작을 때 등) 출사를 자동으로 고름.
- `renderAlloc()`(둔전 배분 추천 카드)도 자원별로 "성지보상 +N, 둔전 × N, 출사 × N" 형태로 소스를 구분해 표시하도록 다시 씀.
- **완료까지 카드의 부제**도 "상자·둔전 포함" 같은 고정 문구 대신, 실제로 기여한 소스만 **메뉴 박스가 놓인 순서(둔전 → 성지보상 → 출사)** 그대로 나열하도록 변경(`al.dtUsed`/`al.sacredPerRes`/`al.csUsed` 각각 0보다 클 때만 포함).
- **버그 하나 고침**: `saveState()`의 저장 객체 리터럴에 `sacred` 키가 이미 원본(천하결전) 생산량 탭의 "성지" 자원 입력(`sacred_w/i/s/f`)용으로 존재하고 있었는데, 새 "성지 보상 서신" 저장 코드도 실수로 같은 `sacred` 키를 써서 **객체 리터럴 중복 키로 뒤엣것이 앞엣것을 덮어쓰는 바람에 저장이 안 되는 상태**였음. `sacredLetters`로 키 이름을 바꿔 충돌 해소.

jsdom으로 세 소스를 동시에 설정(둔전 3회+성지 10레벨 1통+출사 2회)해 검증: 부제가 정확히 "둔전·성지보상·출사 포함" 순서로 표시되고, 배분 패널의 석재 합계(성지 8만 + 둔전 3×5만 + 출사 2×8만 = 39만)와 식량 초과분(성지로만 8만 들어왔는데 필요량이 0이라 스필 8만)까지 전부 정확히 일치함을 확인.

### 8.5-15 책서 자연 회복 배지 (같은 세션)
"보유 책서" 입력칸 옆에 `+N` 배지(`#scrollRegenBadge`)를 추가 — 책서가 시간당 1개씩 자연 회복된다는 규칙(§7 game-mechanics 메모)에 따라, **지금 목표가 완료되기까지 걸리는 시간(res.eta) 동안 자연 회복될 책서량**을 자동 계산해 보여줌(`Math.floor(res.eta * SCROLL_REGEN_PER_HOUR)`). `syncDuntian(res)`에서 함께 계산.

**주의**: 책서 저장 상한(기본 30, 분성 건설 시 50)은 이번에 반영 안 함 — 배지가 상한을 넘는 숫자를 그대로 보여줄 수 있음(hover 툴팁에도 명시). 지금 "분성이 지어졌는지" 여부를 추적하는 상태가 없어서, 상한까지 반영하려면 별도 토글이 필요함 — 다음에 필요하면 추가.

jsdom 확인: 목표 없을 때 배지 빈 문자열, 목표 설정(완료까지 12일 22.2시간=310시간) 시 배지 "+310"으로 정확히 일치.

### 8.5-16 책서 자연 회복이 둔전 가능 횟수에 반영되도록(고정점 계산) + 정적 분석 버그 3건 수정 (같은 세션)

**기능**: "둔전 가능 횟수는 지금 보유한 책서만이 아니라, 완료까지 걸리는 시간 동안 자연 회복될 책서까지 감안해서 자동으로 늘어나야 한다"는 요청 반영. 문제는 순환 관계라는 점 — 책서가 많을수록 둔전을 더 쓸 수 있고, 둔전을 더 쓸수록 완료 시각이 당겨지고, 완료 시각이 당겨지면 그동안 회복되는 책서 양이 줄어든다. `allocate()`를 `runAllocation(dtTotalUses 고정)` + `duntianPlan(고정점 탐색)`으로 나눠서 해결: 둔전 총 횟수를 추정 → 그 횟수로 배분 계산 → 결과 eta로 회복량 재추정 → 횟수 갱신 → eta가 더 안 변할 때까지 반복(최대 20회).

**이어서 요청받은 "소스코드 정적 분석 후 이상 없으면 커밋/푸시"를 진행하며 실제로 버그 3건을 찾아 고침**(모두 이번 세션에 새로 만든 배분 엔진 코드에 있던 것들 — 기존 로직/서버 데이터는 안 건드림):

1. **고정점 수렴 조건이 한쪽으로만 판정되던 버그**: `nextTotalUses <= dtTotalUses`일 때 멈추도록 했었는데, 이러면 초반에 부풀려진 추정치(예: 89회)에서 병목이 바뀌어 진짜 필요 횟수(예: 23회)로 내려와야 하는 상황에서도 멈추지 않고 그냥 이전의 부풀려진 숫자를 "총 사용 가능 횟수"로 잘못 보여줬음(실제 배분·자원량·완료시각 자체는 영향 없었음 — "나머지 N회 아껴둠" 문구만 부정확했음). `nextTotalUses === dtTotalUses`(양방향 수렴)로 수정.
2. **극단적으로 큰 입력값에 대한 안전장치 부재**: 보유 책서/출사 횟수에 비정상적으로 큰 수(예: 999999999999)를 넣으면 그리디 루프가 그 횟수만큼 반복하며 브라우저가 멈출 수 있었음. `MAX_ALLOC_ITER = 3000` 상한을 두어 계산에 쓰는 횟수 자체를 잘라냄(jsdom 실측: 상한 적용 전 예상 시간 vs 적용 후 119ms).
3. **동률 병목에서 그리디가 멈춰버리는 버그**: 두 자원(예: 목재·철광)이 정확히 같은 시간으로 동시에 병목일 때, 그중 하나에만 배분해도 완료 시각(eta = 병목 중 최댓값) 자체는 안 줄어들기 때문에 "eta가 줄어드는 후보만 채택"하는 원래 그리디는 아무것도 못 고르고 멈췄음(둔전·출사가 남아있어도 안 씀). eta가 같으면 "자원별 소요 시간의 합"이 더 작아지는 쪽을 고르는 2차 기준(`sumHours`)을 추가해, 묶인 병목을 한 자원씩 갉아먹어 다음 판에 진짜로 줄어들게 함. (수정 전: 목재·철광 둘 다 60.75시간에 묶여서 출사 재고가 남아도 완료 시각이 그 이상 안 줄었음 → 수정 후: 셋 다 정확히 채워서 "완료까지 즉시"까지 도달.)

**추가로 확인해달라고 하신 "여러 자리 숫자를 입력해도 마지막 자리만 남는" 예전 버그**(원본 프로젝트에서 두 차례 고쳤던 포커스/캐럿 문제, `Documents/PORTING_GUIDE.md` §1 참고)는 이번 파일에서는 재현되지 않음을 확인 — 로스터 표는 `renderRoster()`(전체 재생성)를 타이핑 중에 절대 호출하지 않고 `syncRoster()`(활성 입력칸은 `document.activeElement !== ti` 가드로 건드리지 않음, DOM 노드 자체도 안 바꿈)만 쓰기 때문에, 원본이 겪었던 "재생성 시 포커스 끊김"·"`.focus()`가 값 전체를 선택해 다음 키 입력이 덮어쓰는" 두 문제 모두 애초에 발생할 구조가 아님. jsdom으로 로스터 목표 칸("88")·보유 자원("123456")·성지 서신("25")·둔전 획득량("75000")·보유 책서("999")에 한 글자씩 순차 입력해 전부 끝까지 정확히 남는 것 확인.

### 8.5-17 입력 상한 강제 (같은 세션)
- **건물 현재/목표 레벨**: `data-k` 입력 핸들러에서 `bMax(건물명)`으로 즉시 클램프. HTML `max` 속성만으로는 타이핑 자체를 막지 못해서(브라우저가 값 초과 입력을 허용함) JS에서 값을 눌러 실제로 `t.value`를 덮어씀.
- **자원류 입력 전반(9999999 상한)**: 보유 자원/시간당 생산량/수동 입력/둔전 1회 획득량 입력칸에 공통 `class="cap-input" data-max="9999999"`를 붙이고, `input` 이벤트 맨 앞에서 상한을 넘으면 즉시 잘라내는 공용 처리를 추가(개별 필드마다 따로 안 고치고 한 곳에서 처리). 마우스 휠 증감(`wheel` 핸들러)도 원래 `el.max` HTML 속성을 그대로 참조하므로, `max="9999999"` 속성도 같이 넣어 휠로도 상한을 못 넘게 함.
- **보유 책서(50 상한)**: 같은 `cap-input` 메커니즘에 `data-max="50"`/`max="50"`을 줘서 별도 처리. 단 **책서 자연 회복 배지(`#scrollRegenBadge`, §8.5-15)는 그대로 상한 없이 표시** — 사용자가 "+되는 수치는 50 넘어도 되지만 진짜 최대는 50이라는 걸 명심"이라고 명확히 구분해서 요청함.

jsdom 확인: 군왕전(최대 10레벨)에 "999" 입력 → 10으로 즉시 클램프, 목재에 99999999 입력 → 9999999로 클램프, 보유 책서에 999 입력 → 50으로 클램프(단 30처럼 정상 범위 값은 안 잘림), 회복 배지는 +1030처럼 50 넘는 값도 그대로 표시. 기존 다중 자리 입력(정상 범위)도 여전히 안 끊기는 것 재확인.

### 8.6 검증
jsdom 헤드리스로 구조 확인: 4개 아코디언(내정 9·군사 19·수비 3·분성 7 = 38개 건물, 첫 카테고리만 open), 수동 입력이 어떤 `<details>`에도 속하지 않음, `#verdict`가 `#tab-target`의 첫 자식이자 `.layout`보다 앞, `#needBody` 카드가 `.layout`보다 뒤, 효과 칸이 목표 레벨 변경에 따라 실시간으로 갱신(예: 창고 "최대 자원 +20000" → 레벨3 목표 시 "+20000 → +50000"), 분성-군왕전/분성-민가 비용이 원본과 완전히 동일함을 모두 확인. 콘솔 에러 없음.
